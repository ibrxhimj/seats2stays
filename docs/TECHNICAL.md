# Seats2Stays: technical reference

The full engineering notes: how to run, rebuild and test the project, what every module does, the API, the front end,
the data conventions and the complete limitations list.

> **Public copy.** The competition data, everything derived from it (`data/processed/`, the app bundle), the generated
> reports (`reports/`) and the independent reviewer's workspace (`review/`) are not included: the data is licensed for
> use within the ATP 2026 competition only. Paths to those folders below describe the project as it runs with the data pack.

## Run the simulator

**With Docker (one command; needs no Python, no internet at run time):**

```bash
docker compose up --build        # then open http://localhost:8000
# or:  docker build -t seats2stays . && docker run --rm -p 8000:8000 seats2stays      (make docker-run)
```

The image is built in three stages on `python:3.12-slim`: (1) the exactly pinned packages of `requirements-app.txt`;
(2) the data bundle, the 34 aggregated files the simulator needs (1.1 MB, sha256-listed in `bundle_manifest.json`),
copied from the project's processed tables and checked by running a scenario — the build fails if it does not run;
(3) the runtime: packages, code, web page and bundle, running as a non-root user with a health check. No raw competition
files, no Excel files and no passenger- or guest-level tables are in the image. The page needs nothing from the internet
(D3, the map and the fonts are vendored in `web/vendor/`, tested). It uses about 300 MB of memory; the page answers within a few seconds of starting
and the preset scenarios are ready after about 10.

**Without Docker:**

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-app.txt        # the app only;  requirements.txt adds what rebuilding the data and the tests need
PYTHONPATH=src python -m atp.api           # http://localhost:8000   (or: make app)
```

Python 3.12 or 3.13. The full test suite (272 tests) passes on 3.12 with exactly the versions in `requirements.txt`:
`PYTHONPATH=src pytest tests` (the browser tests need Playwright's Chromium and are skipped without it).

## Reproduce everything from the raw files

```bash
make rebuild        # = scripts/clean_rebuild.sh ../atp2026_rebuild python3.12
```

Copies only the sources (code, config, the five raw competition files, reference and external inputs) to a new folder, installs the pinned `requirements.txt` in a fresh virtual environment, runs every phase (`make data phase1 phase2 phase3 phase4data`) and compares every headline number, data table and generated report with this project's snapshot (`reports/phase5_rebuild.md`). About 2 hours on 2 cores, most of it fitting the hotel-stay model. Verified on Python 3.12 (rebuild) against 3.13 (project): all 184 numbers and all four generated reports identical; 136 data files byte-identical, the other 11 identical in content.

## Independent review

```bash
make review         # rebuild review/inputs, rerun the reviewer's own code, compare with our outputs
```

A reviewer that never saw this code re-derived the key numbers (hotel data handling, ε and its windows, the new-route rate,
aircraft sizes, every test-window and back-test score, range coverage, the SCAD comparison) from the raw files, following
`review/claims.md` (definitions, no values). Its code, results and notes are in `review/`; the comparison and what we did
about every point it raised are in `reports/phase5_review.md`.

## Limitations

<!-- limitations:start -->
_Generated by Step 5.9 (`python -m atp.phase5 limits`); in this public copy, absolute figures from the licensed data are removed._

**What the data cannot see**

- **Abu Dhabi airport only.** Guests who arrive through Dubai or by road sit inside each country's response, not counted passenger by passenger: China has 1.82 hotel check-ins per Abu Dhabi seat. 6.6% of check-ins come from 12 nationalities with no flights in the data; they use the new-route response.
- **Demand shocks are not flights.** War, travel advisories, visas and currency move guests directly. In March 2026 flights explain 26% to 36% of the fall in check-ins; the rest is the demand lever, which the user sets.
- **Stranded travellers are not modelled.** When airspace closes, passengers who cannot fly on check in. On 24 Jun 2025 international check-ins were ×1.11 the same weekday of the three weeks before: 0.3% of June's check-ins and 0.1–0.2% of its guest nights. On 28 Feb 2026, the first day of the 2026 conflict, ×1.31. Real but small, so no term is added.
- **After a disruption, stays are shorter than usual.** Stranded travellers stay one or two nights, not their nationality's usual stay. After 24 Jun 2025 the stay model, given the actual check-ins, over-counted guests by 6.2–8.9% on the next four days (normal June days: +0.0% ± 3.2%). There is one such event in the data, too few to learn a rule from; 28 Feb 2026 is the last day of the data.
- **Stays change in a shock.** In March 2026 guests stayed longer than usual. Stays are normal unless the user changes them with the stay lever.
- **No prices and no room limit.** Hotel rates and airfares are not in the data, so demand reacting to price is outside the model. A scenario above the highest number of guests in-house in the data is flagged, not capped.

**The seat link**

- **Seats partly follow demand.** Airlines add seats where demand is rising: seats two months ahead predict today's check-ins (coefficient +0.15, 95% range +0.01 to +0.28). The response is controlled for this and tested on unseen months, but it is a response seen in the data and used as an assumption, not a proven causal effect, so a pure capacity decision may achieve less.
- **The response depends on leaving out the largest seat changes.** With every change kept it would be 0.54 (0.61 without the control for seats following demand) instead of 0.31. On unseen months the trimmed value predicts better (best single value 0.37, inside the 80% range 0.20–0.43).
- **The response moved over time.** Estimated on data to Jul 2024 it is 0.56, to Dec 2024 0.51, to Jul 2025 0.31; by half-year 0.49 / 0.53 / 0.26. The cause is not established; the final value was confirmed on Aug 2025–Feb 2026.
- **Sustained changes only.** The response comes from month-on-month changes a year apart, so it describes schedules that last weeks or months, not one extra flight on one day; changes shorter than 28 days are flagged.
- **Very large changes are extended, not estimated.** Below −29% the response is a straight line. When Wizz Air left Abu Dhabi, check-ins fell 40% relative to other countries, against 25% predicted at the central value; the range for deep cuts covers it. Above +109% the same line gives more than the fitted curve would, so very large additions may be overstated.
- **Countries without flights borrow their response.** A new route from one of the 12 is worth 0.048 check-ins per seat (80% range 0.022–0.103): ε × the median check-ins per seat of countries that already fly here, with a leave-one-out band. The range leaves out the response's own uncertainty; adding it widens it to 0.020–0.109.
- **One response all year.** It may be lower in winter than in summer (difference −0.18, 95% range −0.41 to +0.06), not significantly.

**How sure the numbers are**

- **One country at a time is noisy.** A single country's month is off by about 18% in both held-out periods, against 3.4% and 6.8% for the international total, so country figures carry wider ranges.
- **Most of a flight result's range is the response itself.** For 10% more seats on every route over the winter, 93%–96% of the uncertainty is the check-in response and the rest the forecast level; for one country (India) 66%. A narrower response needs more seat changes with known outcomes.
- **The 80% range was set on two periods, not confirmed on a third.** Its width was chosen so both held-out periods reach 80% (80.4% and 80.7%), so those figures describe the choice rather than confirm it. The two periods share January and February 2025, and one size group of countries reached only 76% in one direction. The international total's monthly range is the widest gap seen in 14 months and is not calibrated: in each period the other period's range would have held 43% and 100% of months. A single country's own range would hold 43%–50%, which is why ranges are pooled by country size.
- **The response's range comes from one test window.** Its 80% range, 0.20 to 0.43, is the sampling error of a single check on Aug 2025–Feb 2026, not how the response may drift over time, nor a causal range. A bootstrap on the training data gives a wider 0.15 to 0.49.
- **Months 8 to 12 are untested.** In months 1 to 7 after the data the error does not grow with distance (14% in month 1, 17–22% after, one country at a time); the 80% range held 71%–91% of countries by month ahead, least in the middle months. Nothing is known beyond month 7: results from October 2026 are flagged.
- **UAE residents are the hardest series.** On the official test window their forecast was worse than repeating last year (daily 14.9% against 11.6%, bias +6%), and the bias changes sign between periods (+8%, −4%). No flight lever moves them.
- **A machine-learning model does better on some totals.** Given the same inputs, LightGBM is less accurate country by country (in both held-out periods), but it beat our model on international total by day in the second period; international total by month in the second period; UAE residents by month in the second period. It cannot run scenarios through the chain or give a range, so it is not used; the gap on totals is unexplained.
- **Tested on the flights that actually flew.** Every back-test was given the seats that operated, including cancellations; a forecast made from published schedules in advance would be somewhat less accurate.

**Using the tool**

- **Holidays inside Ramadan are untested.** In 2026 Ramadan covers the national holidays of Kuwait and Saudi Arabia, a combination the data never show; the model multiplies the two effects.
- **The test window was scored once.** It was scored with the first version of the check-in forecast; later versions were chosen on the two earlier periods only and never scored on it.
- **Scenarios act from the first day.** A scenario applies the response to each day's passengers at once, while the normal-year forecast smooths seats over 7 days. Over weeks the two agree; in the first days of a sudden change the scenario moves faster than the forecast would. Changes in how full planes are or in connecting passengers use the seat response, an assumption without separate evidence.
- **Built for a desktop screen.** The app works at laptop widths and above; on a phone the evidence tab scrolls sideways.

## Simulator API (Phase 4)

```bash
make app                                   # http://localhost:8000 — engine loads in ~1 s, presets ready a few seconds later
ATP_ROOT=build/bundle make app             # the same, on the app bundle only
curl -s localhost:8000/api/presets/etihad | curl -s -X POST localhost:8000/api/run -H 'content-type: application/json' -d @-
curl -s localhost:8000/api/moves           # the "What moves guests" tab: levers, market × month grid, planner rules (Phase 3 tables)
curl -s localhost:8000/api/know            # the "How we know" tab: back-test, country catch, March 2026 replay, assumptions, limits
```

**Check-in response.** The chain's one estimated step, how strongly a country's hotel check-ins follow its inbound
passengers (ε, and the per-seat rate for countries without flight data), is adjustable like every other assumption:
`"response": "low" | "central" | "high"` on a scenario (and `&response=` on `/api/lever`) shows the result at the
central estimate or at either end of its validated 80% interval (ε 0.197 / 0.312 / 0.426: 10% more inbound passengers
give +1.9% / +3.0% / +4.1% check-ins). The 80% range stays the model's, taken around the result shown; the live lever
still equals a full run at every setting (tested). In the app: "Check-in response" in the scenario rail; pin a result as
A, switch to Low, and the comparison shows what the planning stance is worth. Demand and stay-length changes are
assumptions themselves and do not depend on it.

**Input limits.** A scenario the engine cannot honour is refused with a plain 422, never a 500: every number must be a
finite number (no text, booleans, NaN or infinity) within seats −100% … +1,000%, flights a week 0 … 1,000 (the new-route
form takes up to 100), seats per flight up to 900, percentage changes −100% … +1,000%, transfer-share points ±100, load
factor and local share above 0 and at most 1; dates must be dates inside the horizon; each change must be an object.

Speed (this machine): a market's lever curve 0.1–0.4 s once (19–90 KB gzipped), then every slider position is local;
a scenario with its 80% range 0.3–0.6 s (Etihad's launches 0.5 s); the 325-change March 2026 replay 3.5 s
the first time, then instant (presets are computed at start-up); flights needed for a target ~0.1 s. Phase 4.2 made the engine
faster without changing what it computes: a scenario is resolved once per result (not once per range end), routes and days are
selected on integer codes, Stage B builds its lag matrices as one sliding window, and the stay-length lever's root search starts
next to the answer (results identical; stay-length results within 1e-9, checked on 209 scenarios).

## Key data conventions (details in `reports/data_card.md`)

- **Guests** = guests in-house that night; monthly guest nights = sum of daily Guests.
- **Flights**: monthly in 2022, daily from 2023-01-01. Daily tables start 2023-01-01, so no daily lag can
  touch a monthly aggregate; all lags use date arithmetic (`atp.lags`), never positional `.shift`.
- **Suppression**: hotel rows < 10 are absent (train: by guests; test: by arrivals). Hidden arrivals are filled
  with one documented constant and flagged; hidden guests are never used as targets. Bound: < 0.01% of guests.
- **Calendar**: official UAE public-holiday dates 2022–2026 (`calendar_events_official.csv`) override formula dates;
  a row with `active=False` removes a holiday. `is_long_break` = holiday + adjacent weekend (matches the official
  'actual break' for all 19 cases). School breaks drive `is_school_break` and `school_break_days_left` (family
  return wave). Remaining unconfirmed dates are listed as a warning in the data card.
- **Nationality vs country**: hotel data count guests by nationality, flights by departure country (AUH only).
  `DOMESTIC` = UAE residents of every nationality (on National Day only Domestic rises; expat nationalities fall).
  Airspace-closure days (≥ 3-day interruptions of a running service) are excluded from airline defaults and per-seat ratios.
- **Calendar verification (3 Oct 2026)**: every UAE holiday row 2022–2026 checked against the MoHRE/FAHR announcements
  (private-sector dates = the Cabinet's official holidays, the convention used throughout). Two corrections: National Day
  2023 = 2–4 Dec (was 2–3), 2025 = 1–2 Dec (was 2–3). Forward dates to Feb 2027 are official except National Day 2026
  (scheduled, movable) and Ramadan 2027 (estimated 8 Feb) — listed in `data/processed/phase3/horizon_events.csv`.
